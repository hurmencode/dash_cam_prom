## 📖 Описание

Десктопное приложение для записи видео с промышленных GigE Vision камер
(Lucid Triton, Hikrobot MV-CS) и обычных USB-камер (UVC). Основная задача —
**сбор датасета для обучения нейросети** и **сравнение камер** (нужна ли
дорогая промышленная камера или хватит USB-модуля с глобальным затвором).
Целевая платформа — **NVIDIA Jetson Orin Nano 8 GB** (JetPack 6).

- 🔍 Поиск GigE-камер (Aravis) и USB-камер (`/dev/video*`)
- 📷 Одновременная работа с двумя камерами (одна GigE + одна USB, или две одного типа)
- 🎥 Запись в сегменты по 1 часу, каждая камера — в свои файлы
- 🕒 CSV с номером и временем каждого кадра рядом с каждым видео
- 📸 Снимки (PNG для Mono8/BGR, исходный JPEG для USB в режиме «как есть»)
- 📊 FPS каждой камеры, очередь записи, потерянные кадры, свободное место
- 📋 Логи в окне и в файл `~/dash_cam_prom/logs/session_*.log`

## ✨ Как это устроено (и почему быстро на Orin Nano)

У Jetson Orin Nano **нет аппаратного видеокодера NVENC**, поэтому любое
сжатие идёт на CPU. Главное правило проекта — не кодировать лишний раз:

| Камера | Что приходит | Что пишется | Нагрузка на CPU |
|---|---|---|---|
| USB, отдаёт MJPG | JPEG-пакеты от камеры | **те же JPEG как есть** (`ffmpeg -c copy`) | почти нулевая, без потерь качества |
| GigE, Mono8 | сырые 8-бит кадры | MJPG, качество 95 (настраивается) | заметная |
| GigE, Mono8 (lossless) | сырые 8-бит кадры | FFV1 (`encoder=ffv1`) | высокая, много места |

Остальные решения:

- **Захват и кодирование разделены очередью.** Единственный читатель камеры —
  поток захвата; кадры уходят в рекордер без блокировки. Медленный диск или
  кодек не приводит к потере пакетов на камере; если очередь переполнилась,
  кадры отбрасываются, считаются и показываются красным в интерфейсе.
- **Один поток владеет файлом.** Смена сегмента происходит в том же потоке,
  что пишет кадры, — гонок с закрытием `VideoWriter` нет.
- **Реальный FPS.** Перед началом записи ~1 с измеряется фактическая частота
  кадров (кадры этой секунды не теряются), и файл пишется с ней, а не с
  «30 по умолчанию». При этом запись стартует без блокировки интерфейса.
- **Камера освобождается только после остановки потока захвата** — иначе
  `release()` под работающим `get_frame()` роняет приложение в C-коде.
- **Превью лёгкое:** сначала уменьшение, потом конвертация; не более
  `preview_fps` кадров в секунду; на серых кадрах нет `cvtColor`. Запись от
  превью не зависит.
- **Устойчивость:** защита от заполнения диска, MKV переживает обрыв питания
  (в отличие от AVI без индекса), все исключения (в т.ч. в Tk-обработчиках и
  фоновых потоках) пишутся в лог, при падении в C-библиотеке в файл лога
  попадёт трассировка (`faulthandler`).

## 🚀 Установка (Jetson Orin Nano, JetPack 6)

JetPack 6 — это Ubuntu 22.04 и **Python 3.10**. Пакетный Aravis там версии
**0.8**, приложение работает с ним без сборки из исходников (и с 0.10, если
вы его собрали).

```bash
sudo apt update
sudo apt install -y \
    python3-gi python3-gi-cairo gir1.2-aravis-0.8 arv-tools \
    python3-opencv python3-numpy python3-pil python3-tk \
    v4l-utils ffmpeg

git clone https://github.com/YOUR_USERNAME/dash_cam_prom.git
cd dash_cam_prom
python3 -m venv --system-site-packages .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Проверка Aravis: `python3 tools/check_aravis.py`.

Ярлык на рабочем столе и в меню (пути подставятся сами):

```bash
./install_desktop.sh
```

Если вам нужен Aravis 0.10 — соберите из исходников
(`meson setup build && ninja -C build && sudo ninja -C build install`,
зависимости: `meson ninja-build libglib2.0-dev libxml2-dev
libgirepository1.0-dev libusb-1.0-0-dev`); `run.sh` сам подхватит
`/usr/local/lib/<arch>/girepository-1.0`.

Без `gi`/Aravis приложение тоже запускается — работают только USB-камеры.

## 🎯 Использование

```bash
./run.sh          # или: python3 python_UI/ui.py
```

1. **Камеры → Поиск камер.** Выберите одну или две (Ctrl+Click) →
   **Подключиться**. После подключения камера сразу «живая»: считается FPS,
   работают снимки.
2. **Управление → Папка записи → Выбрать…** (запоминается). Лучше диск NVMe,
   не microSD: непрерывный поток десятков МБ/с карта не держит.
3. **Записать видео** (или `R`). Запись начнётся через ~1 с (прогрев).
4. **Показать / Показать все** — окна превью (можно не открывать).

Горячие клавиши (работают и с русской раскладкой): `R` — запись, `S` —
снимок, `Пробел` — превью, `L` — логи.

Снимки сохраняются в `<папка записи>/snapshots/`.

### Что записывается

```text
<камера>_<слот>_20261022_004407_part001.mkv   # видео
<камера>_<слот>_20261022_004407_part001.csv   # frame_index,camera_seq,unix_time,ae_active
```

`camera_seq` — номер кадра, предложенного рекордеру. Разрыв в нумерации =
кадр отброшен приложением (очередь переполнена или камера отдала битый
JPEG). Потери на самой камере/в сети/USB в нумерации не видны — их видно по
провалам в `unix_time` и по статистике потока в логе. По `unix_time` видна
и стабильность FPS.
Это удобно и для обучения (точная привязка кадров ко времени), и для
сравнения камер: пропуски и джиттер можно посчитать по CSV.

> Для сравнения камер: оценивайте одну и ту же сцену при одинаковой
> выдержке/усилении. USB-камера в режиме MJPG сжимает кадр **внутри камеры**
> (качеством вы не управляете), а GigE-запись — ваше сжатие. Если у USB-модуля
> есть несжатый режим (YUYV), для честного сравнения запишите и его:
> `usb_use_mjpg=false`, `encoder=ffv1`.

## ⚙️ Настройки

Файл `~/dash_cam_prom/config.json` (создаётся при выборе папки записи) или
переменные окружения `DASHCAM_<ИМЯ>`, например `DASHCAM_ENCODER=ffv1`.

| Параметр | По умолчанию | Описание |
|---|---|---|
| `encoder` | `auto` | `auto` — USB-MJPG как есть, GigE → MJPG; `mjpg` / `ffv1` — принудительно кодировать заново (для USB: декодирование + MJPG/FFV1; FFV1 из уже сжатого JPEG смысла не имеет). MJPG/FFV1 кодирует `ffmpeg`, без него — запасной MJPG через OpenCV |
| `jpeg_quality` | `95` | качество MJPG (для обучения не опускайте ниже 90) |
| `container` | `mkv` | `mkv` или `avi` (mkv устойчивее к обрыву питания) |
| `segment_seconds` | `3600` | длина сегмента |
| `min_free_mb` | `5000` | ниже порога запись останавливается |
| `ffmpeg_path` | пусто | путь к ffmpeg, если нужен не из PATH (`DASHCAM_FFMPEG_PATH`) |
| `auto_exposure_seconds` | `30` | автоэкспозиция GigE-камер в начале каждого сегмента на N секунд, затем значение фиксируется; `0` — выключено |
| `auto_exposure_gain` | `false` | заодно подбирать усиление (GainAuto) |
| `queue_frames` | `64` | буфер между захватом и кодированием |
| `write_timestamps` | `true` | CSV с временем кадров |
| `preview_fps` | `15` | предел частоты обновления превью |
| `usb_use_mjpg` | `true` | запросить у UVC-камеры MJPG |
| `usb_passthrough` | `true` | брать сырые JPEG-пакеты (без декодирования) |
| `usb_width/height/fps` | авто | желаемый режим USB-камеры |
| `gige_target_fps` | авто | частота кадров GigE-камеры |

### Автоэкспозиция GigE-камер в начале сегмента

В начале каждого сегмента (в том числе первого) GigE-камера на 30 секунд
переходит в автоэкспозицию, затем подобранное значение **фиксируется**:
внутри сегмента экспозиция постоянна (важно для датасета), а между
сегментами подстраивается под изменившийся свет. Значение пишется в лог
(`экспозиция зафиксирована: 8300 мкс`). Колонка `ae_active` в CSV = 1 для
кадров, снятых во время подбора — их можно исключить из обучения.

- Только GigE (Aravis): GenICam `ExposureAuto` (и `GainAuto`, если включено).
  Если камера не поддерживает — одно предупреждение в логе.
- USB-камеры не затрагиваются: экспозиция остаётся такой, как настроена в
  самой камере.
- После первого окна камера остаётся в **ручном** режиме экспозиции.
- Экспозиция ограничена периодом кадра: при 30 fps не более ~33 мс.

### Оценка USB-камеры (AR0234 и т.п.)

Перед покупкой/выбором режима проверьте, что камера реально отдаёт на Jetson:

```bash
python3 tools/check_usb_camera.py 0 1920 1200 15   # устройство, ширина, высота, секунд
```

Скрипт покажет поддерживаемые режимы, реальный FPS, пропуски между кадрами,
долю битых JPEG, размер потока (ГБ/час) и сохранит `check_frame.jpg`.

### Сколько это весит и тянет ли CPU

Реальный размер зависит от сцены, поэтому замерьте на своём железе:

```bash
python3 tools/bench_encoder.py --mode mjpg --width 1936 --height 1464 --fps 30 --seconds 20 --dir /путь/на/целевой/диск
python3 tools/bench_encoder.py --mode ffv1 --width 1936 --height 1464 --fps 30 --seconds 20 --dir /путь/на/целевой/диск
```

Параллельно смотрите `tegrastats`. «Потеряно: 0» значит, что режим тянется.
Две камеры пишутся независимо — проверяйте суммарную нагрузку.

## 🔧 Настройка Jetson и сети

**Производительность:**

```bash
sudo nvpmodel -q            # текущий режим питания
sudo nvpmodel -m <номер>    # режимы см. в /etc/nvpmodel.conf (выбирайте максимальный)
sudo jetson_clocks          # зафиксировать максимальные частоты
```

**GigE (стабильные 25–30 fps):**

- MTU 1500 (на Realtek r8168 Jumbo Frames 9000 работают нестабильно);
  если у сетевой карты MTU больше — приложение само подбирает размер пакета
  (`gv_auto_packet_size`).
- Буферы сокета (чтобы сохранялись после перезагрузки — в
  `/etc/sysctl.d/99-camera.conf`):

```bash
sudo sysctl -w net.core.rmem_max=33554432
sudo sysctl -w net.core.rmem_default=33554432
sudo sysctl -w net.core.netdev_max_backlog=5000
```

- Отдельная подсеть для камеры, статический IP на интерфейсе Jetson.

**USB 3.0 камеры:** подключайте напрямую в порт Jetson (не через
необслуживаемый хаб), используйте качественный короткий кабель.

## 🩺 Диагностика

- `python3 tools/check_ffmpeg.py` — какие режимы записи ffmpeg тянет.
  Приложение рассчитано и на урезанные сборки Jetson (`--disable-everything`,
  без swscale, протоколы только `file,pipe`): вход идёт через `pipe:0`, JPEG
  копируются демультиплексором `mjpeg`, а формат пикселей готовится в Python.
- В логе `ffmpeg ... НЕ работает в режиме ...` — ffmpeg урезан (нет `image2pipe` или
  протокола `pipe`). Запись при этом идёт через OpenCV (USB-кадры
  перекодируются). Лечится: `sudo apt install --reinstall ffmpeg` или
  `DASHCAM_FFMPEG_PATH=/путь/к/нормальному/ffmpeg`.

- `tools/check_aravis.py` — видит ли Aravis камеры.
- В логе при отключении GigE-камеры выводится статистика потока Aravis
  (`completed`, `failures`, `underruns`). `failures` — потерянные/битые
  кадры, `underruns` — кадры, которым не хватило свободных буферов
  (приложение не успевало их забирать).
- `ARV_DEBUG=stream ./run.sh` — подробная статистика Aravis в консоль.
- «нет кадров более 3 с» в логе — камера перестала отдавать кадры
  (отключена, кабель, питание).

## 📝 Логи

Все сообщения идут в окно «Логи» и в `~/dash_cam_prom/logs/session_*.log`
(записываются сразу, из любого потока). Сохраняются при закрытии окна,
Ctrl+C, SIGTERM, необработанных исключениях; при падении в C-библиотеке в
файл попадёт трассировка потоков. Не спасает только `kill -9` и отключение
питания (но MKV-файлы при этом остаются читаемыми).

## 🛠️ Известные ограничения

- Два слота: одновременно максимум две камеры.
- Авто-переподключение камеры не реализовано: при обрыве запись продолжится
  с пустой паузой (в логе — «нет кадров»), перезапустите запись после
  восстановления.
- GigE-камеры пишутся как Mono8. Цветные/Bayer-форматы не поддерживаются.
- Режим «как есть» для USB требует, чтобы драйвер/OpenCV отдавали сырые
  JPEG-пакеты (`CAP_PROP_CONVERT_RGB=0`); при неудаче приложение само
  вернётся к декодированию и напишет об этом в лог.
- GigE Vision не позволяет двум SDK (Aravis + MVS) работать с одной камерой.
